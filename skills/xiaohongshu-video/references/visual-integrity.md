# 防闪烁与逐帧验收

用于正式新作、Canvas/HUD 浏览器捕获或已发生闪烁的修订。目标是降低捕获错误发生率，并在交付前拦截可检测的视觉坏帧。检测器是筛查工具；零标记不代表所有像素、运动或听感都已获认可。

## 为什么增加这道检查

EP05 v02 的 MP4 能正常严格解码，却混入偶发重复文字块；稀疏代表帧没有覆盖它们。v03 首轮完整捕获仍有十一帧异常，尽管原生短样片正常、已改用 CPU/PNG 捕获。最终通过同帧原生重绘、重新编码、完整连续扫描及邻帧复核排除了已观察的重复瓦片。这个案例支持增加最终文件检查，尚未隔离唯一的 GPU、浏览器或并发根因。

因此分别保留三种证据：捕获配置与就绪逻辑、最终编码逐帧筛查、实际观察/播放。不要把其中一种写成另外两种已经通过。

## 捕获前减少不确定性

- 画面是绝对帧号与固定种子的函数；相同帧重画应相同，乱序渲染也应正确。避免依赖前一帧、真实时钟、未固定随机数、CSS 自行动画和渲染中远程数据。
- 用项目版本支持的媒体组件和 `delayRender` / `continueRender`（或 `useDelayRender`）等待素材与字体；字体就绪后再测量文字。Canvas 必须先完成当前帧绘制，再释放捕获。必要时等待绘制 tick，但不能用固定睡眠替代资源就绪信号；取消、异常和卸载路径也要释放或取消句柄。
- 记录实际 Remotion/Chrome 版本、原生尺寸、浏览器参数、中间帧格式、并发、字体、源文件和 PCM 母带哈希。复用已验证配置，调整时单独验证，不顺手升级依赖。
- 在 Q 的 16 GiB Mac 上同一时刻只跑一项完整 4K 渲染；默认只做小红书，明确增加其他画幅时串行执行；浏览器捕获从较低并发开始，按当前负载和原生样片结果选择。不要把“并发 1”或禁用 GPU 作为确定性证明。需要 WebGL 的工程尤其不能照搬 CPU 开关。
- 对新捕获路径，用**最终原生分辨率**制作覆盖字体首次出现、密集画面、快速运动和转场的短片，带实际字幕与声音。先检查再跑全片；全片仍需独立扫描。

Remotion 官方解释了帧驱动、并发和等待素材的关系：[闪烁排查](https://www.remotion.dev/docs/flickering)、[渲染就绪控制](https://www.remotion.dev/docs/delay-render)。双 RAF、CPU Canvas 和 PNG 中间帧是可测试的具体措施，不是跨机器保证。

## 扫描最终编码

初始化器默认只为小红书新片加入以下必需报告。`platforms`、`outputs` 和 `visual_qc.reports` 的键保持一致；明确增加其他平台时逐个补充对应报告与完整扫描，历史双平台清单继续按原声明检查：

```json
"visual_qc": {
  "required": true,
  "reports": {
    "xiaohongshu": "review/visual-qc-xiaohongshu/report.json"
  }
}
```

从作品目录执行，`N` 使用清单 `total_frames`，不固定写死 7200。每次选择新的报告目录，并将清单中的报告路径指向这次结果：

```sh
python3 <技能目录>/scripts/scan_visual_qc.py \
  --media 小红书/<最终竖版>.mp4 --expected-frames <N> \
  --output-dir review/visual-qc-xiaohongshu
```

脚本需要 FFmpeg/FFprobe、NumPy 和 Pillow；使用工程已有环境，缺依赖时保留未完成，不擅自安装或上传影片。Q 的本机较重检查通过已验证的 `agent-dev run --` 执行。

- 从文件起点连续解码，保持每一帧，不用定时抽样或 seek 代替覆盖；核对实际帧数和解码退出状态。
- 始终筛查整幅缩略图中“异常一帧后迅速回到原状态”的突变。另可按当前版布局增加 `--stable-roi x,y,w,h` 和 `--dark-roi x,y,w,h`。坐标均为 0–1 的归一化范围；前者观察本应稳定的元素，后者观察本应保持暗色的区域。
- ROI 必须来自当前工程，不能照抄 EP05 的水印位置，也不能为检测而给作品硬加水印。没有稳定区域时使用整幅突变筛查，并明确它的局限；渐变、长时间重复、低对比和检测区域外的缺陷仍可能漏检。
- 三帧突变检测对首尾帧和持续多帧的错误覆盖有限；保留首尾代表帧、适用 ROI 与连续播放检查，不能把“解码了每帧”写成“每种视觉错误均已排除”。
- 保存报告、逐帧指标和可疑图。CLI 返回 `0` 表示完整扫描且无标记，`3` 表示完整扫描但需要复核，`2` 表示不完整或错误；都不能直接当作人工观看结论。
- 报告记录扫描前后文件哈希。扫描期间文件变化、解码错误、少帧、多帧或缺工具都不得得到通过。

## 异常逐项处置

对每个标记查看该帧和前后邻帧，必要时查看原生尺寸与正常速度的连续片段。对预期转场同时核对源码边界：转场后的新状态应持续，不能仅凭“它恰好靠近转场”跳过。

保留原始 `flagged_frames`，在 `flag_reviews` 中逐帧记录已实际复核的结果。例如：

```json
"flag_reviews": [
  {
    "frame": 5400,
    "disposition": "authored_transition",
    "note": "已查看前后邻帧并核对时间轴，新场景持续出现。",
    "evidence": {
      "path": "review/transition-5400.jpg",
      "sha256": "<该证据图的实际SHA-256>"
    }
  }
]
```

仅允许 `authored_transition` 或有观察依据的 `false_positive` 清除待复核状态。每个标记需有对应记录、说明和当前工程内的证据文件；未知异常保持未完成。不能删除标记、事后提高阈值到忽略已知坏帧，或用 `artifact_fixed` 文字盖过实际坏片。

确认坏帧时保留失败片，修正捕获/源工程或按同一绝对帧状态原生重绘；不能借用邻帧、插值或删帧来隐藏问题。修补后核对音轨、总帧数和时间轴，并对**新最终编码从头重新扫描**。只检查补过的几帧不足以关闭整片问题。

## 验收与归档拦截

```sh
python3 <技能目录>/scripts/validate_delivery.py <作品目录> --scan-source
```

新项目的必需视觉报告参与最终判定和仓库建归档清单。以下任何一项都会阻止通过：报告缺失/损坏、文件 SHA-256 不匹配、未连续覆盖全部帧、解码失败、标记未逐项复核、证据缺失或哈希不匹配。更换或重新编码 MP4 后，旧报告立即失效。报告中自填的 `PASS` 字样不代替这些字段核对。

历史清单没有 `visual_qc` 时保留兼容，并明确 `NOT_REQUIRED`，不能把旧电影补写成已做过逐帧视觉验收。新作使用当前初始化器；继承旧工程时补齐新策略，不删除它来绕过检查。

即使这些条件均满足，仍继续既有的字幕/安全区/暗部原尺寸检查、运动成对帧、音频测量与播放器测试。在 `review/acceptance.md` 分开记录自动筛查、模型图像观察、连续人工听看和实际设备/App 播放；只填真实已完成的层次。云端 ASR/VL 或上传其他服务仍需相应授权，本地视觉筛查不引入新的云调用。
